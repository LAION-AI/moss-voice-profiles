laion-tts-annotated-v1: what was built, what is inside it, and what is still missing

JUPITER (GH200, 4 GPUs/node) · 2026-08-19 05:45 · corpus at /e/data1/datasets/products/TTS Training Data/laion-tts-annotated-v1
Every number here was produced by a script in $NB/tokcorpus/code/ reading the corpus on disk, and the script is named next to the number.

What this is. A training corpus for text-to-speech (TTS) — systems that turn written text into spoken audio. Modern TTS models learn much better when each recording comes with rich labels: not just what was said, but who-ish said it, how they sounded, what emotion was in the voice, and where the non-word noises (laughs, sighs) fall. This corpus is 130,795,431 utterances / 371,908 audio-hours across 8 datasets and 16,438 shards, each utterance carrying 180 annotation columns.

Headline: the annotation stack is complete. Sampling 400,192 rows spread across all 8 datasets, captions, vocal bursts, all 40 emotion scores, all 57 voice dimensions (regression + bucket), the 4 quality heads, genuineness, blend, and MOSS tokens are at 100.00 % on every dataset. There is no missing-annotation backlog.

Three things were actually wrong, and are now fixed:

  • A single malformed source file could kill a whole worker and forfeit every shard behind it. That — not walltime — is what stalled EuroSpeech at 2,500/2,771.
  • evasnippets' language column was empty for all 500,007 rows because of a one-word config error. Backfilled to 97.68 % without re-running a single GPU stage.
  • A dataset that had never run could never be started automatically — the scheduler sized it at “0 hours of work left”. KartoffelPhon would have sat at zero forever.

0. Vocabulary (skip if you know it)

Utterance
One short recording of speech — typically 5–15 seconds — plus its transcript and labels. The atomic unit of this corpus.
Shard
A bundle of a few thousand utterances stored in one file. Filesystems on supercomputers collapse under millions of small files, so everything is packed into .tar archives (shards) with a matching .parquet table.
Parquet
A column-oriented table file. Reading only the lang column of a million rows touches only that column's bytes, which is why the audits below are cheap.
WebDataset
The convention of storing each utterance as several members of a tar sharing a filename stem: abc123.wav, abc123.json, abc123.moss.npy.
Forced alignment
Given audio and its transcript, computing the time at which each word is spoken. Not transcription — the words are already known; only the timing is inferred.
Vocal burst
A non-word vocal sound: laugh, sigh, gasp, "ahem". These carry a lot of the emotional signal in speech and are usually thrown away by transcript-only pipelines.
Tokenizer (MOSS)
A model that converts a waveform into a short sequence of integer codes, so a language model can predict speech the way it predicts text.
Embedding
A fixed-length vector (here 250 numbers) summarising a recording. Two recordings of the same person land close together; the closeness measure is cosine similarity, which runs from −1 (opposite) through 0 (unrelated) to 1 (identical).
Slurm / GPU-hour
Slurm is the cluster's job queue. One GPU-hour is one GPU busy for one hour. On this machine a whole node is billed whenever any part of it is used, so jobs always request all 4 GPUs.

2. The pipeline — which script produced which annotation

One process per GPU, four per node, launched 150 s apart (four simultaneous cold model loads off the shared filesystem wedge every worker into uninterruptible sleep — a lesson that cost real time). Each source shard flows: read → decode/load audio → resample → scorer → bursts → MOSS → alignment → caption → one output tar + one parquet. A .done marker per shard makes the whole thing resumable and idempotent.

No speech recognition is run anywhere. Every audio-bearing dataset in scope already ships a transcript, so the ASR budget is zero — a large saving that the original plan identified and this build honoured.

Captions are rule-based, not generated. caption2.py maps each VoiceNet head's (dimension, bucket, level-count) to a curated tag and assembles a sentence. Its predecessor sliced the first nine words off a multi-sentence training anchor and produced text like “A The acoustic signature reflects a fully developed, The audio delivers a standard masculine…” Worth knowing when judging caption quality: these are deterministic descriptions, not model prose.

The one real gap: evasnippets' language column — found, fixed, backfilled

The audit showed lang at 0.00 % for evasnippets while every other column sat at 100 %. That shape — one column empty, everything around it perfect — is the signature of a config error, not a failed model. It was:

prodreg.py:  "evasnippets": dict(..., lang=None, ...)
prod.py:519  lang = str(meta.get(cfg["lang"]) or "").lower() if cfg.get("lang") else ""

With lang=None the column is unconditionally the empty string, for all 500,007 rows. The source does carry a language field on the bulk of the set (5,725 of 5,729 rows in the largest shard, 24 languages).

The language was never actually lost from the corpus — prod.py copies the entire source metadata into each output tar's JSON as src_meta, and src_meta.language was intact there. So the repair was a metadata lift, not a reprocessing job: no GPU, no re-download, no re-running the scorer/burst/MOSS/align stack. langfix.py reads it out of the tars and rewrites each parquet to a temporary file which is then atomically renamed — a second agent reads this directory concurrently and must never see a half-written table.

Result (job 1409348, 32 shard-parallel processes, one node): the full 500,007 rows visited, 481,415 language values filled = 96.3 %. Independent re-audit of 12 shards confirms the column on disk went 0.00 % → 97.68 %. The residual ~3.7 % are the small hand-built *_0to1.tar shards whose source genuinely has no language field.

What is still missing, stated plainly

snippets' lang is 0 % and no work was queued for it. Its source JSON has no language-ish key at all — 1,600 records sampled across 8 shards, zero hits. Filling it would require running a spoken-language-identification model, which is a new pipeline stage, not a backfill. That is a decision for whoever owns the corpus, not something to invent here. The same is true of the nonlatin alignment gap: it needs uroman installed, which is an environment change.

4. EuroSpeech: the stall was a bug, not a backlog

The brief said “271 shards remain and the keeper is draining them.” It was not draining. At 23:58 there were zero production jobs queued, the newest .done was two hours old, and the three-generation job chain submitted at 19:57 had ended like this:

jobgenerationoutcome
1407223g0, 8 nodes5 of 8 tasks FAILED, 3 hit the 2 h wall
1407224g1, 4 nodesall 4 FAILED after ~8 min 47 s
1407225g2, 2 nodesall 2 FAILED after ~8 min 48 s

A mop-up generation that burns out in nine minutes is not doing work; it is crashing on the same thing every time. The cause:

File "prod.py", line 449, in process_shard
    items = read_shard(src, cfg)
File "prod.py", line 105, in read_tar_shard
    for m in tf:
tarfile.ReadError: unexpected end of data

Some source archives are malformed. That alone should cost only those shards — but process_shard() was called bare in the main loop, so the exception escaped and killed the worker, forfeiting every shard still on its list. Work is split shard_id % n_workers, so each worker holds shards spread across the whole id range; dying on the first bad archive throws away all the good ones behind it. The 271 were not 271 broken files.

A full scan of all 271 outstanding source archives settled it:

classcountevidence
readable — just never reached246all 246 completed overnight once workers stopped dying: 2,500 + 246 = 2,746 exactly
truncated archive17ReadError, on-disk size equals the published manifest size to the byte
empty archive810,240 bytes, zero utterance members
partially downloaded / absent0—

So 91 % of the “missing” shards were collateral damage, and the 25 stragglers are unusable source files. The truncation is upstream: our copies are exactly the length the repository advertises (e.g. EN-train-00223.tar, 981,556,864 bytes on both sides), so the archives themselves are malformed. The existing size-based guard structurally cannot see this.

Three fixes, because “25 shards left forever” is a runaway

The supervisor (“keeper”) counts any shard without a .done marker as outstanding, and prod.py deliberately refuses to write .done for a zero-item read — because that is also the signature of a reader bug. Left alone, these 25 would be resubmitted every 3 hours until the rearm cap of 200, and the corpus would never be declared complete. It would look healthy the entire time.

  1. Per-shard exception guard in prod.py's main loop. One bad archive now costs one shard instead of a worker's whole list. Failed shards are recorded in the measurement JSON and deliberately left without a .done, so a later re-download is self-healing.
  2. Salvage. read_tar_shard now catches the read error mid-iteration and keeps every utterance read before the damage. Observed live: SR-train-00046.tar yielded 823 recovered utterances, MT-train-00072.tar 751, that would otherwise have been lost.
  3. .skip markers. When a source is provably unusable — it raised a read error and nothing was salvageable, or it is a tiny file with no members — a JSON marker recording the reason is written, and the keeper treats it as not-outstanding. Crucially, a plausible-looking shard that reads zero items still gets no marker and stays outstanding, so a future reader bug is not masked.
  4. The supervisor could see the work but could not submit it. The keeper's own log showed it finding the 25 outstanding shards, calling the submitter, and the submitter answering “nothing left — not submitting” — then re-arming to repeat the identical no-op two hours later. The submitter gated on an estimate of GPU-hours remaining, and the last few shards of any dataset necessarily estimate below the one-hour cutoff, so the gate is guaranteed to misfire precisely at the endgame, on every dataset, every time. It now gates on the actual .done/.skip markers and uses the estimate only to choose how many nodes to ask for.

That is the same root cause as the KartoffelPhon bug in §5: an estimate was being used where ground truth was available. Both failures were invisible in status output — the queue looked healthy, the keeper looked armed, and nothing was happening.

That last distinction matters: an earlier bug in this project split filenames on the first dot, which silently produced 0 items for every evasnippets shard whose name contains "Monotone_vs._Expressive". A blanket “0 items → skip” rule would have permanently buried it.

Outcome (job 1409419). The salvage did better than the scan predicted: all 17 truncated archives yielded recoverable utterances and earned real .done markers. Only the 8 genuinely empty ones — every one exactly 10,240 bytes with no members — were skip-marked, each with a JSON file recording shard, source, byte size and reason, so the exclusion is auditable rather than silent.

EuroSpeech: 2,763 done + 8 unusable = 2,771 / 2,771. Across all eight datasets the supervisor now reports 0 shards missing, so the next wake-up writes CORPUS_COMPLETE and stops re-arming — the self-terminating steady state the design was aiming at, reached rather than merely intended.

5. KartoffelPhon — the new dataset

MultiLlasa/Kartoffelphon-2.5M-de-ger, CC-BY-4.0, German + English podcast speech. It arrives in Arrow format — 207 training + 11 test .arrow files, 100 GB — rather than the WebDataset tars everything else uses, so it needed a new reader.

read_arrow_shard() reads the on-disk Arrow IPC stream batch by batch, so peak memory is one record batch rather than a whole 450 MB shard, and yields the identical item dictionaries the tar reader yields. Nothing downstream is a special case: same five stages, same output tar layout, same 180-column parquet schema.

One subtlety worth recording: uid is built from position in the shard (tr00007_000123), not from the audio path field. The path is an episode-plus-index name that is not guaranteed unique across 207 shards, and uid names the member inside the output tar — a collision would silently overwrite an utterance. The original path is preserved as source_path.

Smoke test (job 1408317, written to a scratch directory so it could not contaminate the corpus with .done markers): 128 utterances, all five stages, no errors. Audited with the same auditfull.py: caption 100 %, bursts 100 %, 40 emo 100 %, 57 vn_reg 100 %, 57 vn_bucket 100 %, 4 qual 100 %, genuineness 100 %, MOSS 100 %, align 100 %, lang 100 %.

Measured cost: scorer 6.24 s + bursts 1.84 + MOSS 3.33 + align 3.17 = 14.58 GPU-seconds for 128 utterances = 114 ms/utterance = 31,600 utterances/GPU-hour. Projected 2.6 M utterances → ~82 GPU-hours.

Result: 218/218 shards, 2,616,656 utterances, 219 index parquets — completed overnight while no agent was alive.

A bug that would have made KartoffelPhon un-runnable by the supervisor

Submitting it the normal way printed “kartoffelphon: nothing left (0 shards done) — not submitting”. The work-sizing helper computes GPU-hours-remaining as rate × bytes_remaining, where rate is measured from that dataset's own completed shards — and a dataset with no completed shards has no measurable rate, so it returned zero, so both the submitter and the keeper skipped it. A brand-new dataset could never be started automatically and would sit at zero forever while the keeper reported everything healthy. Fixed by falling back to the corpus-wide measured rate across the 15.9 k shards that do have history, used only to size the first job.

6. Speaker identity for KartoffelPhon

KartoffelPhon ships no speaker identities. It has a speaker field, but it is a within-episode diarisation label (“SPEAKER_00” = the first voice heard in this episode), so SPEAKER_00 in two different episodes is two different people. It is useless as a global identity — but it is excellent evidence, because two clips sharing an (episode, diarisation-label) pair really are the same person.

Model choice: the identity model, not the timbre model

Two candidate models exist and they are easy to confuse. Their own model cards settle it:

modelwhat its card saysuse here
Orange/Speaker-wavLM-id“produces speaker embeddings for automatic speaker verification”; VoxCeleb1-clean EER 0.946 % at decision threshold 0.388chosen
Orange/Speaker-wavLM-tbr“globally represent the timbral traits… only the timbral traits are compared”rejected

EER (equal error rate) is the operating point where the rate of wrongly merging two different people equals the rate of wrongly splitting one person. Lower is better; 50 % is random.

The timbre model scores voice similarity, so it will happily merge two different people who sound alike — exactly the failure mode that ruins a pseudo-speaker label. The identity model was used.

The loader was broken, and the fix is one line (but not the obvious one)

The first run crashed for every worker:

AttributeError: 'BatchedEmbeddings' object has no attribute 'all_tied_weights_keys'.
Did you mean: '_tied_weights_keys'?
  transformers/modeling_utils.py:4864 in _move_missing_keys_from_meta_to_device

The published model code predates a rename inside the transformers library. The tempting fix — downgrade transformers — would have been wrong twice over: other production jobs share this Python environment, and a package install has destroyed it here before. Instead, a class attribute all_tied_weights_keys = {} is declared on our subclass. It works because the error comes from nn.Module.__getattr__, which is only consulted after normal attribute lookup fails; a class attribute is found first, so __getattr__ is never reached. The empty dict is also the correct value, not a placeholder: this model ties no weights, so the set really is empty and subtracting it is a no-op.

Batching this model correctly is not just about padding

The reference implementation embeds one clip at a time. Its forward pass computes per-utterance mean/variance normalisation and then statistics pooling (mean and standard deviation over time). Every one of those statistics is taken over the whole tensor — so zero-padding a batch does not merely waste compute, it drags the mean toward zero and inflates the variance, changing the embedding. Naive batching here is silently wrong, not just inefficient.

The implementation therefore uses masked normalisation, an attention mask, and masked statistics pooling over each clip's true frame count. That claim is checked, not asserted: a verify mode embeds the same clips both ways and compares.

Verification (job 1409417): 24 clips at a padding ratio of 2.16× (i.e. 116 % of the batch was padding — a deliberately hostile case):

[verify] n=24  pad_ratio=2.16  cos min=0.999927  mean=0.999974

The batched path reproduces the one-at-a-time path to within floating-point noise.

Sanity check: does it actually separate speakers?

A model that loads but emits garbage is worse than one that crashes, so before scaling to 2.6 M clips the embeddings were checked against the diarisation ground truth — 8 speaker groups, 4 clips each, from a real shard:

Separation of 0.662 between the means — unambiguous. The model works.

Throughput (one GPU, 23,788 real utterances = 65 audio-hours, measured end-to-end including Arrow read, MP3 decode and the GPU forward): 72,549 clips/GPU-hour at 199× realtime — i.e. one GPU-node-slice embeds 199 seconds of audio per second of wall clock. For all 2,616,656 KartoffelPhon utterances that is ~36 GPU-hours ≈ 1.1 hours on the 32 GPUs queued. Embeddings are written as parquet keyed by uid, 250-dim float16 in a fixed-size list column, one file per shard — no loose files.

But that number is a property of the node, not of the model. The measurement breaks down as 1,073 s of CPU MP3 decoding against 104 s of GPU time — the GPU is busy only 8.9 % of the wall, and this stage is CPU-bound, exactly like the audio-decode stage measured earlier in this project. The four workers × 16 decode threads already saturate the node's 64 cores, so there is no free win from turning a knob; extracting more would mean fewer GPU workers per node with more decode threads each. Quoting 72,549 clips/GPU-hour as a GPU throughput would be misleading.

One number does vindicate the design: padding waste is 0.22 %. Length bucketing means almost nothing pushed through the network is padding — the masked-statistics implementation is cheap as well as correct.

One number in that table is already load-bearing for the threshold question: at the model card's VoxCeleb threshold of 0.388, all 48 same-speaker pairs are correctly accepted, but 23 of 448 different-speaker pairs (5.1 %) are wrongly merged — far worse than the 0.946 % the card advertises. German podcast audio is not English celebrity interviews. This is precisely why the threshold must be re-derived on this data rather than imported.

7. Choosing the pseudo-speaker threshold — method, not a number

Grouping 2.6 M embeddings into pseudo-speakers requires a similarity cutoff, and the cutoff is the whole ballgame: too low merges distinct people into one pseudo-speaker; too high shatters one person across many. Both damage a TTS corpus, in opposite ways. So no threshold is hard-coded; instead the evidence for choosing one is generated.

Why exact all-pairs is affordable here anyway

2.6 M points is 3.4×1012 unordered pairs — the brief correctly calls that infeasible to materialise. But we do not need the full matrix, only each point's nearest neighbours, since anything below threshold contributes no edge. And because the embeddings are L2-normalised, cosine similarity is the dot product, so the entire neighbour search is one large matrix multiplication.

Method chosen: exact top-k by chunked GPU matrix multiplication — not an approximate index. 2.6 M × 250 in 16-bit floats is 1.3 GB, which sits entirely in a GH200's 95 GB of memory, so there is no approximation at all. Parameters: query block 16,384, key block 262,144, k = 32 neighbours per point, self-matches masked. Total work 2.6M × 2.6M × 250 × 2 ≈ 3.4×1015 floating-point operations — minutes to a couple of hours on one GPU.

An approximate nearest-neighbour index was rejected deliberately: it would add a recall parameter that itself needs defending, on top of the threshold we are already trying to justify.

What the sweep produces

Clusters are connected components under single linkage (if A matches B and B matches C, all three are one speaker). Single linkage is the transparent choice and also the pessimistic one — it is the most merge-happy rule, so a threshold that is safe under it is safe under any stricter rule. For each candidate threshold from 0.30 to 0.85 the sweep reports: cluster count, singleton count, largest cluster, cluster-size percentiles, the false-merge and false-split rates measured against the diarisation ground truth, and example pairs straddling that threshold for a human to eyeball.

Status: the embedding job (1409418, 8 nodes / 32 GPUs) and the sweep (1409431, chained to run automatically after it) are queued and will complete without supervision. The sweep numbers are not in this report — they will be written to $OUT/speaker/threshold_sweep_full.json and a 400 k-subsample safety net to threshold_sweep_400k.json, so a walltime overrun still leaves a complete evidence set.

Provisional recommendation, from the evidence that does exist (the 8-group ground truth above): the VoxCeleb threshold of 0.388 is too permissive for this corpus at 5.1 % false merges. The same-speaker distribution has its minimum at 0.697 and the different-speaker distribution its maximum at 0.773, so the honest crossover lies near 0.70–0.75, and a threshold in that band should be preferred pending the full sweep. Given that merging two people is the more damaging error for speaker-conditioned TTS, and that single linkage compounds merges transitively, err toward the higher end. This is a provisional read on 496 pairs from one shard — treat the queued sweep, which measures ~200,000 positive and 200,000 negative pairs across the whole corpus, as the authority.

9. What would need attention next

  1. Non-Latin alignment. Install uroman and re-run the align stage. Extrapolating each dataset's sampled nonlatin rate to its true row count gives an estimated 5,259,827 utterances (4.0 % of the corpus) that have audio, text and every other annotation but no word timings — commonvoice 2.49 M, eurospeech 2.37 M, podcast 0.39 M. This is the single largest remaining gap and it is an environment fix, not a code fix.
  2. snippets' language. Needs a language-ID stage; 2.6 M utterances currently have no language label and no way to recover one from metadata.
  3. The 25 unusable EuroSpeech archives. Salvage recovers partial content from the truncated ones; a fresh re-download would be needed to know whether the repository has since republished them. They are 0.15 % of the corpus.
  4. Vocal burst class distribution was flagged as suspicious during the survey (a large share of “Low Mumble” and “Ahem”, consistent with the locator firing on low-energy speech). The columns are populated everywhere, but their quality has not been validated by a human listen. That is a labelling-quality question this audit does not answer.
